The last one is particularly important.

Suppose you have:
              Load Balancer
                    |
          ---------------------
          |                   |
       NestJS 1            NestJS 2
          |                   |
          -------- Redis ------


If you store rate-limit counters in Node.js memory, each instance has a separate counter.

Redis provides a shared counter.

This makes rate limiting consistent across instances.

Your Todo application is a good example.

Suppose three users open the same shared todo:
Todo: Complete Redis implementation

Users currently viewing:
  - User 101
  - User 102
  - User 103

Live viewers: 3


Redis can maintain shared presence information across multiple NestJS instances.

One possible structure:
todo:123:viewers
    user:101
    user:102
    user:103


Use a Redis Set for unique viewers, and expiration/heartbeat logic to remove disconnected users.

For WebSocket broadcasting across multiple server instances, Redis Pub/Sub is useful. Remember that Pub/Sub is at-most-once: offline subscribers miss messages. Use Streams or another durable messaging system when replay and reliable processing are required.

Example: Distributed lock

Suppose two customers try to purchase the last available product.
Customer A --------\
                    \
                     NestJS API
                    /
Customer B --------/

       Both request the last item
                  |
                  v
             Redis Lock
                  |
          Only one proceeds
                  |
                  v
             MySQL update


Important: Redis locks are not a replacement for database transactions, unique constraints, or atomic inventory updates. For inventory, use database-level concurrency control as the final protection.

2. Redis data structures and where to use them
Understanding these is more important than memorizing 124 use cases.

Redis has different data structures, and each solves a different type of problem.
Redis data structure	Best production use cases
String	Cache, OTP, counters, tokens
Hash	User profiles, session metadata
List	Simple queues, task lists
Set	Unique visitors, online users, tags
Sorted Set	Leaderboards, rankings, priority queues
Stream	Event processing, durable queues, consumer groups
Bitmap	Daily active users, attendance tracking
HyperLogLog	Approximate unique visitor counting
Geospatial	Nearby drivers, stores, delivery tracking
JSON	Nested objects, document caching
Time Series	Monitoring, metrics, sensor data
Vector Sets / vector search capabilities	Semantic search, AI recommendations

3. My recommended Redis learning priority
Don't try to implement all 124 use cases. Learn the important production patterns first.

   Must learn
   - Strings, Hashes, Lists, Sets

   Must learn
